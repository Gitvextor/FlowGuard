# FlowGuard 开题答辩讲稿

> 适用：国庆后开题答辩。每组 **8 分钟陈述 + 3 分钟问答**。
> 本稿按现有 13 页 PPT 编排，正常语速约 7 分 40 秒，最后留 20 秒收束。

## 一、8 分钟陈述稿

### 0:00–0:35｜封面：我们要解决什么问题

各位老师好，我们组汇报的题目是 **FlowGuard：智能任务护航与中断恢复助手**。

我们关注的不是“用户有没有打开某个娱乐软件”，而是：**这次离开当前窗口，是否仍然服务于正在完成的任务；如果用户被打断，回来时能不能马上知道自己做到哪里。**

FlowGuard 面向 Windows 学习和编程场景，核心结果只有一句话：少误报一次必要查资料，多给出一个可以立刻执行的下一步。

### 0:35–1:15｜问题背景：为什么现有专注工具不够

现在常见的专注工具大致有三种方式。

第一类是 Forest 这样的专注计时和应用阻断：用户开始一段计时，离开应用就会损失可视化奖励。它很适合建立专注习惯，但“离开”本身不等于“偏航”——写代码时切到 Stack Overflow 查当前报错，可能正是必要步骤。

第二类是 Freedom 这样的黑名单和专注会话：通过提前配置要屏蔽的网站或应用来减少诱惑。它解决的是“能不能打开”，但不回答“这次切换是否与当前任务有关”。

第三类是 RescueTime 这样的自动时间记录与报告：它能告诉用户时间花在了哪些应用和网站上，但更多是事后统计，不能在关键切换发生时解释原因，也不能直接告诉用户回来后下一步做什么。

因此，我们把缺口定义为：**现有工具擅长计时、阻断或统计，但缺少任务语义判断和中断后的恢复支持。**

### 1:15–1:50｜研究依据与项目定位

相关的意图驱动多模态研究说明：让用户先声明目标，再把目标和屏幕上下文放在一起分析，比单纯给应用贴“好/坏”标签更合理。

我们的项目不做完整系统移植，也不把论文中的研究结果冒充为 FlowGuard 的实验结果。我们只聚焦一个可验证的 Windows 轻量闭环：**输入任务、读取上下文、分类、记录轨迹、偏航提醒、生成恢复提示。**

### 1:50–2:35｜研究问题与创新点

我们有两个研究问题。

第一个问题是：如何识别必要绕路？我们把行为从二分类细化成三类：**主任务、必要绕路、真正偏航**。主任务是直接推进目标；必要绕路是为解决当前问题而临时查资料、查文档或调试；真正偏航是与目标无关的娱乐或无目的浏览。

第二个问题是：偏航或中断以后，如何帮助用户恢复？FlowGuard 生成一个 Resume Anchor，包含三项：刚才做到哪里、正在解决什么、下一步建议做什么。证据不足时明确写“不清楚”，不编造代码行号和错误原因。

所以我们的增量不是再做一个计时器，而是把“判断”和“回来”连起来。

### 2:35–3:20｜目标与边界

国庆版本只承诺一个能运行、能演示、能评估的闭环。

输入是用户主动填写的任务；上下文包括 Windows 前台应用、窗口标题和必要时的内存截图；输出是三分类结果、近期时间线和恢复提示。

我们明确不做浏览器 URL 深读、OCR、RAG、Agent、自动控制电脑、多设备同步和大规模用户研究，也不新增一个模糊的“无法判断”类别。这样可以把工程风险控制在课程项目可完成的范围内。

### 3:20–4:05｜系统架构

系统采用事件触发式分层架构。

第一层 Windows Context 读取前台窗口和进程信息，并做约 1.5 秒的变化防抖；第二层 Activity Classifier 只有在上下文明显变化时才请求模型；第三层 Session History 保存任务、时间、应用、窗口标题、状态和简短摘要，不保存截图；第四层 Resume Anchor 根据最近几条记录生成恢复提示；最后由 PyQt6 界面展示结果，并只在真正偏航时给一次 Windows 通知。

这样做有两个好处：一是减少重复截图和模型调用，二是让网络请求不会卡住界面。模型出错时，系统保留历史并给出可理解的回退提示，而不是直接退出。

### 4:05–4:55｜一次完整使用流程

演示主线是一个调度实验任务。

用户先输入“完成 Priority Scheduling 实验并整理报告”，在 VS Code 中工作，系统显示主任务。

接着切到 Stack Overflow 或相关文档，虽然离开了 IDE，但窗口内容仍然服务于当前报错，系统标记为必要绕路，不弹干扰通知。

如果再切到 Bilibili 娱乐页面，系统结合目标、窗口和屏幕上下文判断为真正偏航，只提醒一次，不替用户自动关闭页面或操作电脑。

用户返回 VS Code 后，界面显示刚才的轨迹，并给出 Resume Anchor，例如“上次在调度函数文件中；具体未解决错误不明；下一步回到该文件继续验证”。

### 4:55–5:35｜界面设计

界面遵循三个原则：先看当前判断，再看证据，最后看怎么回来。

顶部是任务输入和开始/暂停；中间用三种颜色显示主任务、必要绕路和真正偏航；旁边是最近时间线，用户可以看到状态变化而不是只看到一个分数；底部是 Resume Anchor，把“恢复工作”作为主操作结果。

视觉上采用深色画布、明确的状态色和短文本卡片，避免把用户再次拉进复杂设置。截图处理只在内存中进行，并在界面中明确提示隐私边界。

### 5:35–6:25｜评测方案

我们准备三组可复现情景：直接写代码、查当前错误、打开无关娱乐页面。每个情景有人工标注的三分类标签。

指标包括三分类 Accuracy、Macro-F1、必要绕路的 Precision/Recall、平均模型调用次数和偏航通知冷却是否生效。

同时设置一个简单基线：只要离开主工作 App 就判为偏航。这个基线不是论文算法，而是为了直接展示：在“写代码到查资料”的场景中，三分类是否真的减少了误报。

### 6:25–7:05｜产品落地与简要分工

为了把产品做成可运行闭环，我们把工作拆成四个模块：基础架构负责统一模型、接口、截图和本地会话；Windows 上下文负责前台窗口和变化触发；AI 逻辑负责三分类、结构化解析和可信恢复锚点；产品交付负责 PyQt6 界面、通知、评测与打包。

四个模块共享同一套 `app.core` 数据结构和协议。这里的分工只是保证产品链路完整，答辩重点仍然是用户问题、产品闭环和可验证结果。

### 7:10–7:40｜预期成果与收束

最终交付包括：Windows 可运行包、固定演示流程、评测脚本、测试结果、开题答辩材料和备份演示视频。

我们希望证明的不是“AI 能监督人”，而是一个更具体的工程命题：**当用户必须离开当前窗口时，系统能否理解这次离开是否合理；当用户回来时，系统能否让他从正确的位置继续。**

以上是我们的开题汇报，谢谢各位老师，下面进入问答。

## 二、3 分钟问答备答

### Q1：为什么不直接用 Forest 或 Freedom？

它们分别擅长计时、奖励和阻断，产品完成度很高。我们的研究问题不同：不预先把某个 App 判成好或坏，而是结合用户当前任务判断一次具体切换是否合理，并在中断后给出恢复信息。FlowGuard 是在明确边界上的补充，不是替代成熟专注工具。

### Q2：查资料和刷视频都在浏览器里，怎么区分？

不只看 App 名称。系统把任务文本、窗口标题和必要时的屏幕截图一起交给分类器，输出三类状态；同时保留置信度和简短理由。证据不足时降低置信度，不擅自编造细节。

### Q3：模型判断错了怎么办？

首先，通知只在真正偏航时触发并有冷却，不会连续打扰。其次，所有事件先写入本地历史，模型失败不会导致程序退出。最后，评测会单独报告必要绕路的 Precision/Recall，错误类型可以被定位，而不是只看一个总分。

### Q4：截图会不会泄露隐私？

截图默认只在内存中压缩和发送，不写入 Session Store。用户可以暂停监控；界面明确说明调用外部模型时会发送截图。课程版本不做云端数据库和长期个人画像。

### Q5：为什么不加入“无法判断”类别？

本项目先固定三分类，便于完成闭环和做可复现实验。对于证据不足的场景，我们用置信度、理由和保守的 Resume Anchor 表达不确定性，而不是扩大类别导致评测口径不稳定。

### Q6：你们的创新够不够？

我们不把“多模态判断”本身宣称为绝对首创。项目创新点是面向 Windows 学习/编程场景的工程化组合：把必要绕路从二分类中拆出来，把事件触发降低调用成本，并把偏航判断连接到有证据的恢复锚点。最终用基线和情景评测验证这三个增量。
